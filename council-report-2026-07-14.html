LLM Council · verdict

Card game standings tracker — requirement review

5 advisors, anonymized peer review, chairman synthesis · 2026-07-14
The question

Is the PRD for a 4-player card game standings tracker a flawless requirement before any build? Locked: strictly 4 players, exactly 1 loser per game, one admin logs everything, no per-user accounts. Standings show games played, losses, and rank, sortable by most wins and by lowest loss rate.

Mid-review the requirement changed from "single device" to a web app with data that stays consistent across devices. That change resolves the council's number-one finding, so the verdict below already accounts for it.

COUNCIL VERDICT

Where the council agrees

  1. "Wins" is a fiction. With 1 loser per game, 3 people "win" every time, and games-not-lost = GP − L is redundant with the two numbers beside it. Relabel it and add a one-line legend. Stop filing the definition as an open question.
  2. Persistence was the fatal flaw. On one device with no export, a dead phone erased everything. Promote shared storage and export to P0. Your new cross-device web-app requirement fixes this directly.
  3. Keep the build small. Rename-with-history, full retroactive edit, adjustable threshold, and heavy season machinery are gold-plating for a 4-friend scoreboard.
  4. Close the illegal-edit hole. Any edit must still enforce exactly 4 players and 1 loser, or the admin can save a broken record.

Where the council clashes

Scope. The Expansionist wants delight features (loser of the night, rivalries, streaks) in P0 because the real job is bragging rights. The Executor and 3 reviewers say that is building the second floor before the ground floor, since persistence was not even solved. Resolution: fix persistence and the "wins" relabel first, then add just one cheap ritual (loser of the night) that serves the stated rivalry pain. Defer the rest to P1.

Do you need two sorts? First Principles showed both rankings give the same order when everyone plays equally, so a fixed group that always shows up needs only one. Others keep both because you asked. Resolution: keep both, state the overlap plainly, fix the contradictory tiebreak, and settle it by asking the 4 players how often the lineup changes.

Blind spots the peer review caught

  • One admin, forever. Every number depends on one person logging every game. A few skipped or misremembered nights distort loss rate silently, with no audit trail. This is a habit risk, not a feature.
  • A permanent loser board can sour the game. Default to the skill view and show the positive number first.
  • Cheapest unblock: ask the 4 players what a "win" means to them and how often the lineup changes. No advisor proposed it.

The recommendation

Ship a hosted web app with a shared backend so data persists and stays consistent across devices. Single admin writes via a passcode-gated edit mode; everyone else opens the same URL and sees a live read-only standings. Keep P0 tight: log a game (enforcing 4 players and 1 loser on create and edit), live standings with both sorts and a legend, undo-last, persistent shared storage, and export. Relabel "wins" as games not lost. Add one delight hook, loser of the night. Defer head-to-head, streaks, and season awards to P1.

The one thing to do first

Lock the data model and hosting: one shared URL, one backend table of game rows (timestamp, 4 player slots, loser), admin writes gated by a passcode, everyone else read-only. Everything in the standings is derived from that table. Prove it persists across two devices before building any UI polish.

FULL ADVISOR RESPONSES

The Contrarian▸
Looks for what will fail

The single sharpest flaw: the PRD treats a decided constraint as an open, blocking question. Section 11 lists "single device vs. sync" as blocking and Section 12 calls it the gating dependency. That is locked. Delete it. Worse, the "no cloud, single device" constraint manufactures a data-loss risk the PRD never mitigates: weeks of standings and archived seasons live on one device with no P0 backup, and export is buried in P1. One lost phone erases everything. Export and backup belong in P0. This is the actual fatal flaw.

Section 7.5 lets the host change the roster, but no acceptance criterion re-asserts the invariant: editing must still force exactly 4 players and 1 loser. You can edit a game into an illegal state. In lowest-loss-rate mode, provisional players get no rank, so half the required sort modes leaves some people rankless. "Most wins" is near-degenerate: with W = GP − L and a 25% loss rate, wins track games-played by construction. Open Question #4 defines the group's core word "win"; resolve it before build.

The First Principles Thinker▸
Rebuilds the problem from scratch

You documented the model beautifully and answered the wrong question. In a 4-player, 1-loser game there are no winners. The only atomic fact the app records is a loss. "Wins" (W = GP − L) is a derived, redundant column carrying zero information beyond GP and L. The group asked for wins; you gave them arithmetic. The honest label is "games survived."

Is dual-sort the real need? It only produces two orderings when attendance differs. For a fixed group who mostly all show up, when GP is equal, "most wins" descending and "lowest loss rate" ascending are the same list. Dual-sort is a symptom of not knowing how variable attendance is. The actual job is a roast machine; the emotional payload is the loser. Raw losses and loss rate answer "who is the biggest loser" and "who is genuinely good" cleanly. Contradiction: the most-wins tiebreak (Section 8 row 4) breaks ties by "fewer games played," importing skill logic into the activity ranking. One axis per sort, or drop the second.

The Expansionist▸
Looks for the upside everyone missed

The PRD is engineered like a spreadsheet. It captures a timestamp, full roster, and loser per game, a richer event log than the standings table ever spends, and that surplus is the real upside, buried in P1. Three near-zero-cost payoffs: "loser of the night" is one grouping away, an instant recurring ritual and screenshot bait. Rivalries via head-to-head need no new inputs, and the problem statement literally names "weak rivalry" as the pain then exiles the cure to P1. Streaks turn a static table into a live story: "Ade has not lost in 6."

Then compound it for free: season awards at reset, auto-generate a "season wrapped" card (champion, biggest loser, longest streak, fiercest rivalry) from archived data, zero new schema. The PRD undersells itself: it frames success as logging speed, but the moat is memory and bragging rights. Promote loser-of-the-night and head-to-head into P0.

The Outsider▸
Zero context, reads only what is there

The "wins" problem is worse than the open question admits. Three people win every game, so "wins" never means "beat someone," it means "showed up and was not the loser." Since W = GP − L, the W and L columns are mathematically redundant: three columns that are really two. Cut W, or label it "games not lost." Loss rate as the default "who is best" view inverts normal standings intuition: rank 1 holds the lowest number, while every scoreboard a newcomer has seen puts the biggest number on top. Expect confusion.

The 25% luck line is well-reasoned but invisible to a stranger: the table only styles sub-25% players with no legend. Terminology drifts between "provisional" and "not enough games yet"; pick one. Contradiction: 7.2 says "default 4," implying changeable, while non-goal 3 says locked at 4. "Season" is never defined. And Appendix A's Eka, who never lost yet ranks last in most-wins mode, looks broken to anyone who does not grasp the model.

The Executor▸
Can it be built, and what is the first step

Simplest thing that works: a single HTML file with local storage, or a spreadsheet with one row per game and a pivot for standings. Everything in the scoring model is derivable from that one row. Genuinely needed P0: log a game, standings, the two sorts, undo-last. Gold-plating dressed as P0: archive-player plus rename-with-history, full retroactive edit of any past game, season reset with read-only archives, and a host-adjustable threshold (hardcode 5).

Where a builder stalls: storage is unspecified; backup is absent and this is the real flaw, since one dead phone erases everything and export is buried in P1, so promote export and backup to P0; tiebreaks are fine. Monday morning: build one page, hardcoded 4 names, tap-loser and save, computed standings with a sort toggle. That slice tests the 10-second, 3-tap goal tonight.

PEER REVIEW HIGHLIGHTS

What the reviewers converged on▸

Strongest responses: the Contrarian (widest set of real defects, only one to catch the illegal-edit hole) and the Executor (turns critique into a Monday build). Both named the missing backup as fatal.

Biggest blind spot (all 5 reviewers): the Expansionist, for promoting delight features onto a foundation that could not yet persist a single night. "Building the second floor before the ground floor exists."

What all five advisors missed:

  • The single-admin single point of failure and logging discipline. If the admin is absent or forgets, the record is silently wrong, and there is no audit trail.
  • The social risk of a permanent "biggest loser" board among friends.
  • The cheapest resolver for the "what is a win / how many sorts" debate is to ask the 4 players.
Verdict: build a shared web app, keep P0 tight
